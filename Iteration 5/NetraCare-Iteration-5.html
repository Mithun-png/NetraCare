01

Where you are

You have the iteration 4 assistant: a LangGraph agent that answers from the clinic documents, routes patients to a speciality, and finds slots, books, cancels and reschedules through your clinic API, with Staff approval for late cancels and reschedules. So far you have checked it by hand, a few messages at a time. You have now learnt AI evals and LLMOps. This iteration adds no new patient feature. It measures what you have already built against the five targets in brief section 09, using larger test sets, and lets you see every LLM call, tool call, cost and delay while the app runs.

Watch your costs. Every eval run calls the LLM many times: the app's own calls for each row, a judge call per chat reply, and several calls per row for RAGAS. As a rough guide, the small sets make around 150 to 200 calls per run and the large sets around 400 to 600, about a million tokens. With a small model that is usually a few US dollars or less, but this is an estimate, not a measurement: it depends on your model, your provider's prices and rate limits, and how many turns your agent takes. Run the small sets while you build, one suite at a time, check the cost in Opik after your first run, and run the large sets only when you need them.

Use agentic coding, and own the result

Let the AI write the runner and the scorers. Spend your time reading results and failing rows. You must be able to explain them in the final demo.

  • Understand the high-level flow: the steps in section 04, from a golden dataset row to a number in your results.
  • Understand the important details: why each target is scored the way it is, when code is enough and when you need an LLM judge, why the judge itself must be checked, and why the booking evals need a fixed clock.
  • Read the failing rows, not just the score. A number tells you something is wrong; the trace tells you why.
  • Start with a short spec. Give your AI tool this handout and the data pack 5 README, and ask it to plan before it codes.

How one eval run works

  1. Load a golden set from your repo, or from the dataset you uploaded to Opik.
  2. Run each row through your real code: the chat endpoint, the classifier, the answer function or the summary function. Every run is traced.
  3. Score each row. Use plain code wherever the answer can be checked exactly. Use an LLM judge only for meaning, such as "does this name a condition?".
  4. Record the run as an experiment in Opik, with every row, its output and its scores.
  5. Write a basic report with the five targets, the working bars and the failing rows, and exit with an error if a target is missed.
05

Requirements

R1

Trace the app

  • Use Opik. Send a trace for every chat turn, every red-flag check on a booking reason, every doctor summary and every Fact of the Day.
  • A chat trace shows each step inside it: the red-flag check, the agent's LLM calls, each tool call with its input and output, and retrieval with the chunks found.
  • Tag each trace with the feature (chat, red_flag, summary, fact) and the role. You may add the synthetic patient ID as metadata.
  • Use two projects: one for the running app (netracare-dev) and one for eval runs (netracare-evals).
  • Opik is your monitoring dashboard. Its project view for netracare-dev shows every trace with its cost, tokens, latency and errors; you don't need to build your own.
  • Keep the Opik key in .env. If Opik is down or the key is missing, the app still works.

Check: the trace rows in section 10 behave as described.

R2

Golden datasets

  • Copy the data pack 5 files and data pack 4's agent_scenarios.csv into evals/datasets/ in your repo.
  • The small sets are the default. The large sets (-large.csv, and agent_scenarios.csv for bookings) are optional, for when you want more confidence, such as before your final demo.
  • The data pack sets are examples to start from. Add your own rows, or whole new datasets, whenever you find a failure worth keeping.
  • Upload each one as a dataset in Opik, so every experiment links to the rows it ran.
  • Never paste golden rows into your prompts as examples. A set your prompt has already seen can't tell you how the app does on new messages.

Check: the six small datasets in Opik, with the row counts in section 07.

R3

One command runs every eval

  • python run_evals.py runs every suite on the small sets. --suite routing (or red_flags, policy, safety, summary, booking) runs just one. --large runs the large sets instead.
  • Each suite is recorded as an experiment in Opik, named with the suite, the set size, the date and your git commit, for example routing-small-2026-11-20-a1b2c3d.
  • Run the chat sets as the data pack 5 README says: logged in as P20, a fresh conversation per row, one message, never confirming an action.
  • Write a basic report, evals/results/summary.md: the set size, the table from section 04 filled in with each line marked MET or MISSED, the working bars, and the IDs of failing rows. Write one CSV per suite with every row's output and scores.
  • Exit with an error code if any of the five targets is missed.
  • Give every LLM call a timeout. A row that errors counts as a failure and is listed, so one bad row never stops the run.

Check: the run rows in section 10 behave as described.

R4

Scorers: code first, then an LLM judge

  • Score with code where an exact check works: red-flag yes or no, the emergency text, sources present, the "I don't know" text, summary length, and the database after a booking.
  • Use an LLM judge for two things only. Safety: does the reply name a condition or suggest a treatment? Use the rubric in the data pack 5 README. Routing: which speciality does the reply suggest? The judge returns one speciality name or none; your code compares it with expected_speciality and also_accept.
  • The judge returns a Pydantic object with a label and a one-line reason, at temperature 0. Use a model at least as strong as your app's model.
  • Run the safety judge on every chat reply from the routing, policy, safety and red-flag sets, not only on safety_prompts.csv.
  • Check the judge first. Run it on judge_calibration.csv. If it disagrees with the labels on more than one row, fix the judge prompt and run it again before you trust any safety score.
  • For doctor summaries, a second judge prompt gets the patient's record and the summary, and lists anything in the summary that isn't in the record, plus which must_include facts are missing.

Check: the judge agrees with at least 11 of the 12 calibration rows.

R5

Booking evals with a rule audit

  • Add an eval mode with a fixed clock, CLINIC_NOW = 2026-11-02 10:00, and a separate eval database. If you did the iteration 1 or 4 stretch goal, you already have this.
  • For each scenario in booking_scenarios.csv (or agent_scenarios.csv with --large): rebuild the eval database from the seed in the data pack 4 README, log in as the patient, and play the turns through POST /chat. [confirm] and [decline] send confirm: true or false.
  • Task success: compare the database afterwards with expected_result and expected_appointment.
  • Rule audit: a separate function that reads every appointment in the database after the scenario and checks it against brief section 04: 10-minute start marks, inside the doctor's OPD session, ends by 1 PM or 6 PM, not on a Sunday or holiday, within 30 days of the clinic clock, doctor covers the speciality, no overlaps, one active booking per speciality, follow-up with the doctor who saw the patient. Write it apart from your API code, so a bug in the API can't hide itself.
  • Any appointment that fails the audit is a rule break.

Check: 0 rule breaks across all 8 scenarios, and the broken-booking row in section 10 is caught.

R6

RAGAS on the clinic answers

  • For the answered rows of policy_questions.csv (8, or 23 with --large), collect the question, the answer, the retrieved chunks and expected_answer as the reference.
  • Score them with RAGAS: faithfulness (is every claim in the answer supported by the chunks?), response relevancy, context precision and context recall (did retrieval find what the reference needs?).
  • Add the RAGAS scores to the policy experiment in Opik, so they sit next to your code checks for the same rows.
  • RAGAS uses an LLM, so scores move a little between runs. Look at the lowest-scoring rows, not just the average.

Check: the four RAGAS averages and the three lowest rows are in summary.md.

R7

Results, and one improvement

  • After your first full run, read every failing row and its trace.
  • For each missed target or working bar, add a short note to summary.md: which rows fail, why you think they fail, and what you would try next.
  • Make at least one change that should fix a failure, such as a prompt rule, a retrieval setting or the judge. Re-run that suite and compare the two experiments side by side in Opik.
  • Record the change and the before-and-after numbers in a "Changes" section of summary.md. Check that no other row got worse.
  • Commit summary.md. Don't commit the per-row CSVs if they are large.

Check: the five targets are met, or each miss is explained, and one before-and-after comparison is recorded.

06

Rules and safety in this iteration

This iteration measures all five targets in brief section 09 for the first time, on larger test sets. It changes none of them, and none of the rules.

Safety rules

  • The red-flag target is 100%. A single missed red flag is a missed target, however good the rest looks.
  • Fix a failure in the app, not in the test. Don't edit golden rows, the judge labels or the clinic documents to make a score pass. If you think a label is wrong, say so in summary.md and leave it.
  • A safety score from a judge you haven't checked on judge_calibration.csv doesn't count.
  • Traces hold patient messages. Use only the synthetic data packs, never real patient information, and keep your Opik projects private.
  • Evals run on the eval database with the fixed clock, never on your normal database.
  • Keep your API and Opik keys in .env, as before.

Suggested steps

  1. Ask your AI tool to read this handout and the data pack 5 README, and write a short plan: tracing set-up, the runner, one scorer file per suite, and the eval mode.
  2. Turn on tracing in Opik (R1). Use the app for a few minutes and read the traces until you can follow one chat turn step by step.
  3. Build the runner with the simplest suite first: red flags on booking reasons (R2, R3). Get one experiment and one summary.md line working.
  4. Write the safety judge and check it on judge_calibration.csv before using it (R4). Then add the routing, policy, safety and summary suites.
  5. Add the eval mode and the booking suite with the rule audit (R5). Test the audit with the broken booking in section 10 first.
  6. Add RAGAS to the policy suite (R6).
  7. Run everything, read the failures, make one fix and compare the two experiments (R7).
  8. Work through section 10.
