04

How the agent works

Each patient message runs through a small LangGraph graph. The agent node loops with the tools node until it has an answer, and pauses for the patient before anything changes.

  1. Red-flag node. Your code runs check_red_flags on the patient's message. A red flag ends here with the emergency response, an urgent case and no tool calls.
  2. Agent node. The LLM gets its instructions, today's date and a 30-day calendar, the patient's appointments and past visits, and the conversation. It replies, asks a question, or asks for one or more tools.
  3. Tools node. Runs the tools the LLM asked for and returns the results to the agent node. The loop repeats until the agent replies, up to a step limit.
  4. Confirm. Before a book, cancel or reschedule reaches the API, the graph pauses and the patient sees a card with Confirm and No. Nothing changes until they confirm.
  5. The API decides. The tool calls the same rules check as your website. A refusal comes back with its reason code, and the agent explains it and offers free times instead.
  6. Your code finishes the reply. It adds the sources from any document search, as in iteration 3, and shows the card or the answer.

Who decides what

DecisionMade by
Which tools to call, which free time to offer, how to explain a refusalThe agent (the LLM)

R1

Finish the clinic API

  • Reschedule (a stretch goal in iteration 1; reuse it if you built it). It is one action: check the new booking as if the old one were already cancelled, then cancel the old one and book the new one together. If the new booking is refused, the original stays exactly as it was.

  • The patient comes from the login, never from the LLM. Pass the patient's ID to the tools through the graph's config, not as a tool argument, so the LLM can't act for someone else.

Check: call each tool from a Python shell as a patient, including one refusal and one appointment that belongs to someone else.

R3

The agent graph and its prompt

  • Build a StateGraph yourself with three nodes: the red-flag node, the agent node (the chat model with the tools bound to it) and a tools node, as in section 04. Set a step limit; if it is reached, the chat shows "Sorry, I can't finish that just now. Please try again, or ask Staff at the front desk."
  • Build the system prompt for every message, from the database:
    • Today's date, weekday and time, and the next 30 days, each with its weekday and "open" or "holiday", so "next Saturday" is never a guess.
    • The patient's name and age, their upcoming appointments, and their past visits (date, doctor, speciality, visit type). Leave out doctor notes and the health profile; the agent doesn't need them.
  • The prompt tells the agent to:
    • find free times with find_slots before offering any, and never offer a time it hasn't seen there;
    • ask for the reason for the visit before booking;
    • book a follow-up with the doctor who saw the patient last in that speciality, and a new consultation otherwise;
    • pick the speciality before looking for slots: a patient under 16 always books Paediatric (Dr. Menon), whatever the problem; and when a patient describes a problem instead of naming a speciality, such as "my eyes hurt when I read the board", use the same speciality routing as your iteration 3 chat;
    • explain a refusal in plain words and offer free times, or say clearly when nothing is free in the next 30 days;
    • keep the iteration 3 rules: no conditions, no treatment, nothing outside NetraCare.

Check: the multi-step rows in section 10 offer the times described.

R4

Conversation memory

  • Add a LangGraph checkpointer (InMemorySaver) and give every chat a thread_id. The browser sends only the new message and the thread_id; the checkpointer keeps the conversation.
  • Send the agent at most the last 20 messages, so long chats stay fast.
  • "New chat" and logging out start a new thread_id. Nothing from the chat is saved to the database, apart from what the tools do and urgent cases.
  • The iteration 3 rewrite step goes away: the agent writes a standalone question when it calls search_clinic_docs.

Check: "Actually, make it the afternoon" works in the same chat, and logging out and back in shows an empty chat.

R5

Confirm before every action

  • book_appointment, cancel_appointment and reschedule_appointment call LangGraph's interrupt() with a one-line summary before they call the API, for example Book Dr. Kiran Shah, Retina follow-up, Fri 13 Nov, 9:00 AM (10 min)?
  • The chat shows the summary on a card with Confirm and No. The answer resumes the graph with Command(resume=...). On No, nothing changes and the agent asks what the patient would like instead.
  • POST /chat takes {thread_id, message}, or {thread_id, confirm: true|false} from the card. While an action is waiting, its response includes pending_action. A typed message while an action is waiting counts as No, and the agent then handles the new message.

Check: no appointment changes in the database until Confirm is pressed.

R6

Red flags and clinic answers in the agent

  • The red-flag node checks every typed message, as in iteration 3, with the same emergency response, urgent case and failure message. The booking API also still checks the reason, as in iteration 2.
  • search_clinic_docs returns the iteration 3 answer, its sources and whether it answered. Your code adds the Sources: line under the agent's reply from that result. The agent never writes sources itself.
  • If the documents don't cover the question, the tool returns the fixed "I don't know" message and the agent passes it on word for word.

Check: the red-flag, sources and "I don't know" rows in section 10 behave as described.

R7

Doctor leave and Staff rebooking optional

Optional. Try it if you have time after R1 to R6. It completes the last rule in brief section 04.

  • Add leave to the rules check: no booking in a session the doctor has marked as leave (reason code DOCTOR_ON_LEAVE), and free slots skip those sessions.
  • A doctor marks leave for a date and AM, PM or the full day, within the next 30 days.
  • Your code then works through the affected appointments in time order. This is a fixed set of steps, so it is plain code, not an agent. For each one it cancels the appointment and proposes a new time, using your free-slots function:
    • A new consultation: the earliest free slot, at or after the original time, with any doctor who covers that speciality. If only that doctor covers it, this is their next free slot.
    • A follow-up stays with the same doctor: their next free slot.
    • A tie goes to the original doctor, then to the lower doctor ID.
  • Save each proposal as an appointment with the status proposed. It holds the slot. If nothing is free within the 30-day window, say "No slot: call the patient".
  • Staff see a rebooking list and click Approve, which makes it booked, or Reject, which frees the slot. The patient sees "Moved because Dr. … is on leave", with the new time once Staff approve it.

Check: pick a Monday in the next few weeks that is not a holiday. As Staff, book with Dr. Rao that day a new Cataract consultation at 10:00, a new General consultation at 10:20, and Asha Verma's Cataract follow-up at 11:00. As Dr. Rao, mark that Monday as leave. All three are cancelled, and Staff see three proposals: Cataract with Dr. Iyer at 10:00 that Monday, General with Dr. Shah at 10:20 that Monday, and Asha's follow-up with Dr. Rao at his next free time (Tuesday at 9:00 if that day is open and free). After Staff approve them, Asha sees the new time and why it moved, and the chat won't book Dr. Rao that Monday.

06

Rules and safety in this iteration

The agent can now change the database, so 0 bookings that break a clinic rule is the target that matters most here. It adds two rules from brief section 04: rescheduling, and Staff approval inside 2 hours. Doctor leave, the last one, is optional (R7). All the other targets from iterations 2 and 3 still hold in the chat. Iteration 5 measures them on a larger test set.

Safety rules

  • Every chat message goes through the red-flag check first. A red flag gets the emergency response and an urgent case, and the agent books nothing.
  • The API decides every booking, cancel and reschedule. The agent can never skip a rule, and its tools can never write to the database directly.
  • Nothing changes until the patient presses Confirm. A late cancel or reschedule waits for Staff.
  • The patient's ID comes from the login. The agent only ever sees and changes that patient's appointments.
  • The chat never names a likely condition and never suggests treatment. Answers about policy or procedure show their sources, or "I don't know".
  • If the red-flag check can't run, the chat doesn't answer or act.
  • The agent's prompt has no doctor notes or health details. It doesn't need them to book.
  • Use only the data packs. Keep your API keys in .env, as before.
