04

How the chat answers

Every patient message goes through the same steps. Your code runs them in order; the LLM is used in steps 1, 2 and 4.

  1. Red-flag check on the patient's message, using check_red_flags from iteration 2. A red flag stops here with the emergency response.
  2. Rewrite the question using the recent conversation, so a follow-up such as "What should I avoid after it?" becomes "What should I avoid after cataract surgery?".
  3. Hybrid search with the rewritten question: keyword (BM25) and vector search together, top 4 chunks.
  4. Answer from those 4 chunks only. The LLM returns the answer, the IDs of the chunks it used, and whether the chunks answered the question.
  5. Your code adds the sources from the chunks' file and section, or shows the fixed "I don't know" message.

Two kinds of search, used together

Keyword search (BM25)

Scores chunks by the words they share with the question. Rare words count more than common ones, and a word repeated many times stops adding much.

Good at exact terms: HbA1c, RGP, LASIK, a doctor's name. Misses a question that uses different words.

Vector search (embeddings)

Turns the question and every chunk into vectors, and finds the chunks closest in meaning.

Good at the patient's own words: "the operation to straighten his eye" finds Squint surgery. Can miss a short code or a rare exact term.

Hybrid

Runs both and merges the two ranked lists, so a chunk that either search ranks highly makes the top 4.

This is what the chat uses.

05

Requirements

R1

Build the knowledge base

  • Load the three documents in documents/. Split each one on its ## headings first, so every chunk belongs to one section. Split a section again only if it is longer than your chunk size (about 1,000 characters, with 100 overlap).
  • Give every chunk its metadata: source (file name), section (heading) and a chunk_id.
  • Embed the chunks and store them in Chroma or Weaviate. Build the index with one command, such as python build_index.py, and run it again when a document changes. Don't rebuild on every request.

Check: the index has about 38 chunks (one per section, more if your chunk size splits some), and every chunk has its file and section.

R2

Hybrid search with BM25

  • Build a BM25 keyword retriever over the same chunks. Lowercase the text and strip punctuation before scoring, so "Menon?" matches "Menon".
  • Combine it with the vector retriever, with equal weight, and return the top 4 chunks. With Chroma, use LangChain's EnsembleRetriever. With Weaviate, you can use its built-in hybrid search with alpha 0.5 instead.
  • Add a search debug view for Staff: type a question and see the top 4 chunks from keyword only, vector only and hybrid, each with file, section and score.

Check: the two search rows in section 10 behave as described.

R3

Patient chat window

  • A chat panel on the patient's page. Only patients can use the chat; the backend checks the role. Messages are up to 500 characters.
  • It remembers the current conversation only. Send the last 6 messages with each request. "New chat" and logging out clear it. Nothing is saved to the database.
  • Before searching, rewrite the patient's latest message into a standalone question using that history (section 04, step 2). A message that is already complete stays as it is.

Check: the follow-up row in section 10 answers about cataract surgery, and logging out and back in shows an empty chat.

R4

Red-flag check before every answer

  • Run check_red_flags from iteration 2 on the patient's own message, before rewriting or searching.
  • On a red flag, the chat shows the emergency response in red, word for word, and does not search or answer that message:
What you describe needs urgent attention. Please come to the clinic now or go to the nearest emergency department. Our staff have been notified.
  • Save an urgent case, as in iteration 2, marked as coming from the chat. It sits at the top of the Staff view until Staff click "Mark seen".
  • If the check fails, show "We couldn't check your message just now. Please try again, or call the clinic if it's urgent." and don't answer.

Check: the red-flag row in section 10 behaves as described.

R5

Answers with sources, or "I don't know"

  • The answer prompt gets the rewritten question and the 4 chunks, each labelled with its chunk_id. It answers only from those chunks, in no more than 120 words.
  • The output parser returns answer, source_ids (the chunk IDs it used) and answered (true or false).
  • Your code shows the sources under the answer, built from the chunks' metadata, for example Sources: procedures.md › Cataract surgery. The LLM never writes the sources itself.
  • If answered is false, or source_ids is empty or names a chunk that wasn't retrieved, your code shows this instead, with no sources:
I don't know. Our clinic documents don't cover that. Please ask Staff at the front desk.
  • Prompt rules: never name a condition the patient might have, never suggest a treatment or medicine, share costs as indicative only, and politely decline anything that isn't about NetraCare.
  • The chat can't see free slots or book yet. Asked to book, it says so and points to the Book page. It may share a doctor's OPD days from doctors.md.

Check: the answer and "I don't know" rows in section 10 behave as described.

R6

Speciality routing

  • When a patient describes a problem, the chat suggests the speciality to book and names its doctors, from doctors.md, with the source. For example: "A Glaucoma specialist can assess this. At NetraCare that is Dr. Meera Iyer. The doctor will assess you at your visit."
  • It never says what the problem might be or what is causing it.
  • Children under 16 go to Paediatric. A patient who isn't sure goes to General. A problem that isn't about the eyes gets a reply saying NetraCare only looks after eyes.
  • Use the same answer chain as R5, with the routing rules added to its prompt.

Check: at least 9 of rows R01 to R10 in routing_samples.csv get the right speciality, and none names a condition.

06

Rules and safety in this iteration

This iteration starts two more targets from the brief (section 09): 100% of policy answers cite a clinic document, and ≥ 90% of patients routed to the correct speciality. It extends two from iteration 2 to the chat: 100% of red-flag messages trigger the emergency response, and 0 answers that name a condition or suggest treatment. Iteration 5 measures all of them on a larger test set.

Safety rules

  • Every chat message goes through the red-flag check first. A red flag gets the emergency response and an urgent case, and no answer.
  • The chat never names a likely condition and never suggests treatment or medicines. It suggests a speciality and says a doctor will assess.
  • Every answer about policy or procedure shows the document it came from. If the documents don't say, the chat says "I don't know".
  • Costs are information only. The chat never takes payments or helps with insurance.
  • If the red-flag check can't run, the chat doesn't answer.
  • Only patients use the chat, and it never shows anyone else's appointments or details.
  • Use only the data packs. Don't edit the documents to make a check pass; fix chunking, retrieval or the prompt.
  • Keep your API keys in .env, as before.

Technology choices

PartUse
RAG frameworkLangChain (required), carrying on from iteration 2: text splitters, embeddings, a vector store, retrievers, and prompt | model | parser chains. LlamaIndex is a stretch goal.
Vector databaseYour choice. Chroma installs with pip and saves to a folder, so it is the easiest start. Weaviate runs in Docker or a free Weaviate Cloud sandbox and has hybrid search built in.
EmbeddingsYour provider's embedding model, such as OpenAI text-embedding-3-small, or a free local one from sentence-transformers. Read the model name from .env. If you change the model, rebuild the index.
Keyword searchBM25, with LangChain's BM25Retriever (it uses the rank_bm25 package).
Everything elseAs in iteration 2.
TestingBy hand, using the checks in section 10. Automated tests are a stretch goal.

Put the RAG code in its own module, for example rag.py: building the index, the retrievers, the rewrite chain and the answer chain. Give each LLM call a timeout. If the rewrite, search or answer step fails, the chat shows "Sorry, I can't answer just now. Please try again, or ask Staff at the front desk."

Suggested new endpoints (adapt as you like): POST /chat (the message and the last 6 messages), GET /staff/search-debug?q=.
