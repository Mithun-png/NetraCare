04

How the pieces fit

NetraCare now has five ways of knowing or doing something. Each has one job. Putting something in the wrong place is the most common mistake in this iteration.

PartHoldsWhen it runsExample
CodeClinic rules and safety rulesAlways, before anything elseRed-flag check, 30-day window
RAGNetraCare facts to look up and citeWhen the agent searchesOpening hours, the cost of cataract surgery
ToolsActions on NetraCare dataWhen the agent calls themFind slots, book, cancel
SkillsKnow-how for a task: steps, scripts, checklistsOnly when the LLM decides a task needs oneLASIK questions, the after-surgery guide
MCPTools shared between apps: yours for partners, and partners' for youWhen a partner calls you, or your agent calls a partnerA partner books for Ravi Kumar; your chat asks CityCare Lab about HbA1c

Anything that must happen every time, such as the emergency response or a booking rule, stays in code. A skill only runs if the LLM chooses to load it, so it can never be the only thing keeping a patient safe.

1 · A partner books through your MCP server

  1. The partner's agent connects to http://localhost:8001/mcp and reads your two tools and their descriptions.
  2. It calls find_slots, then book_appointment.
  3. Your tool calls the same booking code as your website and agent. It never copies the rules.
  4. That code runs the red-flag check on the reason, then every clinic rule, and returns booked, refused with a reason code, or the emergency response.

2 · Your assistant calls CityCare Lab's MCP server

  1. At startup, your app connects to http://localhost:8002/mcp and loads the lab's one tool, get_lab_test_info, next to your own tools.
  2. A patient asks "Do I need to fast for an HbA1c test?". The LLM picks the lab tool from its description, just like one of your own.
  3. The lab's server answers from its own data. Your code shows "Source: CityCare Lab (partner)" under the answer.

3 · A patient message that needs a skill

  1. Red-flag check on the patient's message, in code, as before.
  2. The agent's system prompt lists every skill's name and description only, a few lines in all.
  3. The LLM decides a skill fits and calls load_skill. The full SKILL.md comes back as the tool result.
  4. If the skill says so, the LLM calls read_skill_file for an extra file, or your other tools, such as my_appointments.
  5. The agent answers. Your code shows "Skill: name" under the answer, from the tool calls it saw.
05

Requirements

R1

NetraCare MCP server

  • A separate program, for example mcp_server.py, using the MCP Python SDK. Serve it over Streamable HTTP at http://localhost:8001/mcp, alongside your API.
  • Two tools, named as in iteration 4: find_slots (speciality, date or date range, optional doctor) and book_appointment (patient name, mobile, speciality, doctor, date, start time, reason). Both are for new consultations only.
  • Each tool calls your existing booking code: the service functions behind your API, or the API itself over HTTP. Never write a second copy of a rule.
  • Typed inputs, and a description on each tool and each input that a stranger's agent can follow: date and time formats, the 30-day window, that start times are on 10-minute marks, and that a reason is required.
  • The patient is found by mobile and name, as at website login. A new mobile creates a new patient. A known mobile with a different name gets PATIENT_DETAILS_MISMATCH, so nobody books into someone else's record.
  • Every result says plainly what happened: booked with the appointment details, refused with the reason code and the plain message from iteration 1, or red_flag.

Check: MCP Inspector lists the 2 tools with their descriptions, and rows M01 to M11 of mcp_scenarios.csv behave as described.

R3

Connect to CityCare Lab's MCP server

  • Run the ready-made lab server from the data pack, partner-lab/citycare_lab_mcp.py, in its own terminal. Don't change it. It plays a partner's system that NetraCare doesn't own.
  • In your Patient assistant, load its tools with langchain-mcp-adapters and add them to the agent's tool list. Read the server URL from .env.
  • Under an answer that used the lab tool, your code shows "Source: CityCare Lab (partner)".
  • Add to the system prompt: lab information is general information only. The assistant never says which tests a patient needs, never interprets a result, and can't book lab tests. If the lab doesn't know a test, say so and don't guess.
  • If the lab server isn't running, the chat still starts and works. Lab questions get "I can't check CityCare Lab just now. Please ask Staff at the front desk."

R4

Skills in the Patient assistant

  • Copy the data pack's skills/ folder into your project. Each skill is a folder with a SKILL.md that starts with YAML front matter (name, description), and may hold extra files.
  • At startup, read only the front matter of every skill. Add a short "Available skills" list, name and description, to the Patient assistant's system prompt.
  • Add two tools to the agent: load_skill(name) returns the body of that SKILL.md; read_skill_file(name, file) returns one file from that skill's folder. Refuse an unknown skill, and any file path outside the skill's folder (such as ../).
  • Under each answer, your code shows "Skill: name" for every skill loaded in that turn. Skill files count as clinic documents, so an answer that uses one cites it.
  • Only the Patient assistant has skills. The red-flag check still runs on every message first, and a skill can't turn it off.

06

Rules and safety in this iteration

MCP opens a new doorway into your booking code, so this iteration extends two brief targets (section 09) to partner apps: 0 bookings that break a clinic rule, and 100% of red-flag messages trigger the emergency response. The lab tool and the skills must keep 0 answers that name a condition or suggest treatment.

Safety rules

  • Every MCP booking goes through the red-flag check and every clinic rule, in the same code as the website. A red flag gets the emergency response and an urgent case, and no booking.
  • Your MCP server only finds slots and books. It never shows appointments, visit notes, summaries or any patient's details.
  • The red-flag check and the emergency response stay in code, before the agent. They are never a skill.
  • Lab answers never say which tests a patient needs and never interpret a result. The doctor decides and explains.
  • Skills never name a likely condition, never name or change medicines or drops, and never say whether someone is suitable for a procedure.
  • read_skill_file reads only files inside that skill's folder.
  • Your MCP server has no login, which is fine for a classroom project. A real clinic would add authentication, such as OAuth, and rate limits.
  • Use only the data packs. Don't edit the supplied skills or the lab server to make a check pass; fix your loader, tool descriptions or system prompt.
  • Keep your API keys in .env, as before.
